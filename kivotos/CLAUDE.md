# Kivotos Tactical Frontline

## Goal
- Build the complete single-player web autobattler described in docs/GDD_v2.1.md as amended by docs/GDD_v2.2_amendment.md and docs/GDD_v2.3_amendment.md, plus the OOParts relic system in docs/OOPARTS_v1.md.
- Shipping scope (pack ba-content-2.4.0): 100 units, 63 synergies, 454 parent effect definitions (399 + 55 OOParts),
  12 equipment, 13 strategies, 55 OOParts, 13 enemies, 15 combat nodes, 100 dialogue files.
- These counts describe this content pack, never hard-code them in the engine.

## Authority
- v2.3 amendment overrides v2.2, which overrides v2.1. docs/OOPARTS_v1.md is the source for OOParts. v2.3 replaces the unit and synergy tables entirely; v2.1 corrections override the original content v2.0 (not in this repo).
- Read the relevant GDD chapters and effect entries before implementing a feature.
- Record any additional design interpretation in docs/DECISIONS.md.
- Never run prose placeholders such as skill_op or synergy_op. Effect `spec` text is documentation only.
- Missing effect handlers must fail validation, not silently become no-ops.

## Repository layout (this game lives in kivotos/ of a repo that hosts other games)
- Work only inside kivotos/ except the shared CI workflow and the root service worker exclusion list (tools/build.mjs OTHERS).
- Deployed at /gamecode/kivotos/ — keep `base: './'`. Any service worker, cache or IndexedDB name must start with `kivotos-`.
- src/content/*.json is generated by scripts/extract-content.mjs from docs/. Edit the docs (or the extractor), then run `npm run content:extract`. Never hand-edit the JSON.

## Architecture
- Layers: src/core (pure deterministic TS, no DOM, no packages) → src/content (data) → src/app (GameClient, the UI contract) → src/ui (replaceable screens).
- src/ui may import only src/app, src/content and src/core/types. tests/unit/architecture.test.ts enforces this; tsconfig.core.json compiles core/content/app without DOM.
- The UI is being designed separately and will be swapped in. Never put game rules in src/ui; expose what screens need through GameClient and document it in docs/UI_CONTRACT.md.
- Battle simulation uses seeded independent RNG streams and runs in a Worker.
- Do not use wall-clock time, Math.random, or UI state as combat rules.
- Costs and base SP/energy gains belong only to ActionResolver.
- Ability bodies execute before their resolved events are published.
- Battle and reward settlement must be idempotent and transactionally saved.
- Use local placeholder assets when artwork is unavailable; keep the game playable.

## Workflow
- Track milestones and tested effect coverage in docs/IMPLEMENTATION_STATUS.md.
- Validate source IDs and canonical data before balancing values.
- Implement M0 through M6 (plus v2.2 M2.5 vertical slice); an intermediate prototype is not the final scope.
- Add meaningful boundary and interaction tests, especially turn clocks and chains. Write the failing test first.
- Keep package-lock.json and the Node version in .nvmrc (22).
- Do not remove tests or content to make a build pass.

## Completion
- Run `npm test` and `npm run build` (build runs content:check, content:validate and typecheck first).
- Report commands actually run and failures honestly.
- Report balance/performance as unmeasured unless simulation was actually run.
- Deliver playable dist, README, validation results and known limitations.
